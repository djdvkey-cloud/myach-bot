1. **Меню команд («Функции») — только у Дмитрия.** На старте очищаются default / группы /
   личные / админские / чат-scope (и языковые варианты ru/en), затем меню ставится только для

   при первом запуске). Управление: «👥 Игроки» в панели, привязка проголосовавших кнопками,
   текстовые команды. Поиск по Telegram ID, username, отображаемому имени.
3. **Help администратора** (`/help` в личке, «❓ Help» в панели): разделы Опрос, Игроки, Составы,
   Матч, Статистика, Оплата, Служебные. Тест проверяет, что каждая зарегистрированная команда описана в Help.
4. **Защита статистики:** атомарная запись, копии в `/data/backups` (последние 40, одинаковые не
   дублируются), при повреждении/неверной структуре `stats.json` изменяющие операции останавливаются,
   файл не перезаписывается, Дмитрию приходит понятное сообщение.
5. **Опрос:** один на субботу; автоматически с 12:00 (Екатеринбург), при возврате бота позже в ту же
   субботу создаётся после запуска; ручной `/опрос` в субботу считается субботним и блокирует
   автоопрос; ручной в другой день субботу не блокирует; повторный `/опрос` в тот же день — только `/опрос да`.
6. **Публикация составов один раз:** после успешной отправки кнопка → «✅ Опубликовано»
   (неактивна); при ошибке отправки кнопка остаётся; после изменения состава — новая
   версия («📢 Опубликовать обновлённый состав»).
7. **Ввод результата кнопками** («⚽ Внести результат матча»): игроки из фактического состава,
   голы/передачи ➖/➕, предпросмотр, «✅ Записать матч» / «✏️ Изменить» / «❌ Отмена».
   `/матч` оставлен как резервный способ.
8. **Фактический состав и замены** («⚙️ Изменить состав», `/состав`): добавить (игрок или гость),
   убрать, заменить — «📌 На его место» или «🔄 Пересобрать команды»; история изменений;
   первоначальный состав сохраняется. Гость без статистики — средний коэффициент игроков (прежнее правило).
9. **Оплата по фактическому составу** («💰 Рассчитать оплату»): N из состава, прежняя формула, предпросмотр,
   отправка в общий чат только по подтверждению и один раз для версии состава. `/оплата N` остался.
10. **Живое оформление:** 11 фраз опроса и 10 финальных фраз составов, ротация без повтора подряд
    (последняя фраза хранится в `/data/ui_meta.json`). Только текст сообщения.
11. При каждом запуске бот присылает Дмитрию «🟢 Мяч запущен»: версия, состояние статистики и игроков,
    состояние меню (счётчики команд по scope, тип кнопки меню до/после).

## 4. Модель фактического состава (`game.json`)

`teams` — текущий (фактический) состав по командам; `initial` — первоначальный, не меняется;
`rev` — версия состава (растёт с каждым изменением); `history` — кто выбыл / кто добавлен /
кто кого заменил и когда; `ratings`, `guests` — рейтинги и список гостей; `published_rev`,
`payment_rev` — для какой версии уже отправлены составы и оплата; `result`,
`result_recorded` — черновик и признак записанного результата. Новый `/разделить` создаёт
новую игру, прежняя уходит в архив. Фактический состав используется для публикации, ввода
результата и оплаты. Правило коэффициентов — прежнее (`koef_for_names`): статистика игрока,
иначе рейтинг гостя, иначе среднее известных игроков списка. Совпадение имён — без регистра и «ё/е»,
поэтому один человек не раздваивается в статистике.

Панель `/menu`; `/help`; `/игроки`, `/игрок добавить|удалить|username …`, `/привязать @user = Имя`;
`/разделить` (`/split`), `/добавить`, `/состав` (`/squad`), `/результат` (`/result`), `/матч`,
`/отменить`, `/статистика`, `/переименовать`, `/обнулить да`, `/оплата` (`/pay`), `/опрос`
(`/poll`, `/опрос да`), `/id`, `/отмена`. Права для игроков не менялись (общий чат:
матч, статистика, составы, отменить, оплата, id, help).

## 6. Порядок работы дальше

- Любое изменение начинать со **свежего клона Amvera `master`**, а не с локальной/GitHub-копии.
- После правки: тесты (`python -m unittest discover -s tests`), push в Amvera, затем живая проверка в Telegram;
  логи без проверки живого сценария приёмкой не считаются. `__pycache__` в репозитории быть не должно.
- **Новая admin-функция → обновить `HELP_SECTIONS` в том же изменении** (тест это проверяет).
- Перед зеркалированием на GitHub не затирать более новые коммиты; не публиковать секреты,
  телефоны и списки username в публичном репозитории.

  Дедупликация: маркер `last_poll.txt` (в /data, переживает рестарты) + дата в `poll_state.json` + флаг в памяти `_POLL_SENT_DAY` (если запись на диск
  после отправки не удалась) + `POLL_LOCK`. Старый `poll_state` не блокирует новую неделю (сравнивается дата именно этой субботы); он один, перезаписывается каждый опрос
  (хранит poll_id, message_id, chat_id, date, monday, status, published, published_at, voters, manual).
  **Черновик ≠ опубликован (2026-10-03.3).** Кнопка «🗳 Опрос» → «📢 Опубликовать сейчас» и `/опрос` публикуют опрос в `CHAT_ID` СРАЗУ (предпросмотра нет; первый экран — только
  подтверждение). `published = true` и message_id/chat_id пишутся только ПОСЛЕ успешного `send_poll` (значения — из ответа Telegram); ошибка отправки ничего не фиксирует и
  допускает повтор. Автоопрос блокирует только подтверждённая публикация на ЭТОТ понедельник в общем чате (в т.ч. вручную в другой день); черновик/`published=false`/опрос не
  в `CHAT_ID` не блокируют. Записи старого формата (без `published`) проверяются у Telegram (`poll_message_exists`: пустая правка разметки — «not modified» = сообщение
  есть, «not found» = нет, иначе неясно → не блокирует); новая запись с `published=true` при неясной проверке блокирует. Слои защиты от дубля: маркер субботы, дата в
  poll_state, `_POLL_SENT_DAY`/`_PUBLISHED_MONDAYS` в памяти (если запись на диск после отправки не удалась), `POLL_LOCK`; граница: если после успешной отправки не записалось
  вообще ничего и процесс перезапущен, повтор возможен (message_id опроса есть в логе). Цикл планировщика теперь не умирает от неожиданной ошибки. При запуске в лог и Дмитрию пишется строка
  «🗳 Следующий автоопрос: суббота дд.мм.гггг 12:00 (Asia/Yekaterinburg) на понедельник дд.мм.гггг». Реальный автоопрос в субботу 26.09.2026 ушёл в 12:00:06 по Екатеринбургу.
  Случай 01.10: ручной опрос на 05.10 (message_id 1014, `CHAT_ID`) реально отправлялся (кнопка «✅ Создать опрос» публиковала сразу, лог «Опрос отправлен (вручную)»), но 2026-10-03 Telegram

## 12. Составы: жёсткое правило цвета и ротация «Пересобрать команды» (2026-10-18, версия `2026-10-18.4`)

- **Жёсткое правило.** Ковалёв М. НИКОГДА не попадает в красную команду (может быть в белых или чёрных). Реализация: `TEAM_COLOR_BANS = {norm_key("Ковалёв М."): {"красные"}}`;
  цвет команды берётся из `TEAM_COLORS` (индекс 0 — белые, 1 — чёрные, 2 — красные; тест фиксирует этот порядок), имя сверяется штатной `norm_key` (регистр, ё/е, пробелы).
  Запрет — отсечение вариантов, а не штраф: при полном переборе допустимы только разбиения, которые можно раздать по цветам без нарушения; в эвристике (больше 15 игроков)
  запрещённые обмены не выполняются. Если распределение невозможно — `ValueError`, никогда не молчаливое нарушение. В играх на 2 команды красной нет. Если Ковалёва нет —
  прежний алгоритм (`exact_split`/`heuristic_split`) без изменений. Ручные явные действия администратора («добавить в команду N», «на его место») правило не переопределяют и не проверяют.
- **Почему «Пересобрать» возвращало тот же состав.** `exact_split` — полностью детерминированный перебор без случайности и истории (побеждает первый лучший вариант), а `squad_rebuild`
  звал его с теми же игроками и теми же фактическими коэффициентами → каждый раз один и тот же оптимум.
- **Как теперь.** `pick_split(mode="rotate")`: берутся ВСЕ допустимые разбиения, чей разброс средних коэффициентов (прежняя метрика `max(avg) − min(avg)`) не хуже лучшего более
  чем на `BALANCE_TOLERANCE = 0.15`; текущий вариант исключается всегда, затем последние показанные (`g["split_history"]`, отпечатки до `SPLIT_HISTORY_KEEP = 10`; отпечаток —
  кто с кем, без порядка внутри команды и без цвета); среди оставшихся выбор случайный; если выбор кончился — «прощаются» самые старые варианты истории, но не текущий.
  Если равноценной альтернативы нет — состав и ревизия не меняются, бот пишет «Другого достаточно ровного варианта при текущем составе не найдено» (не «Команды пересобраны»).
  Индивидуальные коэффициенты не меняются — пересчитываются только составы и средние команд. Добавление/замена игрока (`reason` ≠ manual) — лучший вариант без ротации, история начинается
  заново; новая игра (`new_game`) стартует с историей из одного отпечатка. Полный перебор кэшируется (до 16 наборов), первый расчёт 15 игроков ≈ 1 с.
- **Проверка на составе №7 (копия, production не менялся):** 12 игроков, 2 команды; всего ~26 равноценных вариантов (разброс 0.011…0.16); 30 пересборок подряд дали 24 разных
  состава, внутри окна истории повторов нет, разброс средних ≤ 0.15, Ковалёв ни разу не красный (на 15 игроков/3 команды — 300 генераций без единого нарушения, бывает и в белых, и в чёрных).
- **Тесты** 254 (`tests/test_rotation.py` — 19: правило Ковалёва, ротация, история, честное сообщение, новая игра, копия №7).
- **GitHub ↔ Amvera.** Проект `myach-reserve` связан с GitHub: push в `main` репозитория `djdvkey-cloud/myach-bot` автоматически сливается в `master` Amvera merge-коммитом
  (`Merge branch 'main' of https://github.com/...`) и пересобирает проект (виден рестарт). Поэтому GitHub `main` = триггер деплоя: `bot.py` в `main` должен совпадать с production.
  Через слияние в репозиторий Amvera попали и служебные файлы GitHub (`amvera.yml` с Python 3.12 рядом с `amvera.yaml` 3.11, `data/`, `tests/`, `.github/`) — на запуск не повлияли

## 13. Абсолютное правило Ковалёва и единственный production-конфиг Amvera (2026-10-18, версия `2026-10-18.5`)

- **Правило «Ковалёв М. никогда не в красных» — для ВСЕХ способов изменения состава.** Единая проверка `check_team_allowed(name, team_idx)` (цвет из `TEAM_COLORS`, имя через `norm_key`):
  автоделение и «Пересобрать» (отсечение вариантов + итоговая страховка), «Добавить в команду N» (`squad_add`), «📌 Поставить на его место» (`squad_replace_in_place`),
  «Заменить с пересборкой» и «Добавить с пересборкой» (новичок временно кладётся только в РАЗРЕШЁННУЮ наименьшую команду — `smallest_allowed_team`, проверка до любых изменений, состав не портится).
  Нарушающее действие не выполняется, владелец видит «Ковалёв М. не может играть в Красной команде.» (кнопки остаются прежними, блокировка на стороне логики).
  Других путей изменения состава нет (перенос между командами и обмен игроков в боте не реализованы). Тесты: `tests/test_kovalev_paths.py` (13) + `tests/test_rotation.py`.
- **Единственный production-конфиг Amvera — `amvera.yaml`:** Python **3.11**, `singleton: true`, `scriptName: bot.py`, `persistenceMount: /data`, `requirementsPath: requirements.txt`.
  Файл `amvera.yml` (Python 3.12, без singleton) удалён из репозитория; тест `tests/test_deploy_config.py` следит, чтобы он не вернулся.
  История: стабильный production Miami-0 с 12–13.10 работал на `amvera.yaml` (сборки на cp311); `amvera.yml` пришёл 18.10 11:39 UTC автослиянием GitHub `main` (в GitHub-зеркале он лежал с 01.10),
  при двух файлах Amvera применяла именно его (сборки стали cp312). Функциональной причины для 3.12 нет (код и тесты не зависят от версии, зависимости закреплены), утверждённого решения о переходе не было.
- **GitHub `main` связан с автодеплоем Amvera.** Каждый push в `main` репозитория `djdvkey-cloud/myach-bot` автоматически сливается в `master` проекта `myach-reserve` (merge-коммит `amvera`) и
  перезапускает бота. **Push в `main` = production deploy**: делать один финальный push после локальных тестов, `bot.py` и `amvera.yaml` в `main` должны быть теми, что нужны в production.
  Прямой `git push` в Amvera по SSH (раздел 11) тоже работает, но следующее слияние GitHub всё равно придёт — держать оба репозитория согласованными.
- **Один экземпляр бота.** `singleton: true` + `Instances: 1`; при каждом деплое в логе строго «Received SIGTERM» старого процесса → запуск нового, сообщений Telegram `Conflict`
  (два polling-процесса) нет.
